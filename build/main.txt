22   1 Introduction
23   Python programs rely on dynamic typing to express computations over objects with different
24   implementations. The operations performed on these objects impose requirements on their types
25   and supported protocols. When an execution violates those requirements, an operation can fail
26   at runtime. Detecting these failures before execution is therefore an important task for Python
27   software analysis. Type annotations provide interfaces for static checking [19], while duck typing
28   allows code to operate on objects through their behavior [5, 15]. A detector must connect this
29   behavior to the program state at each operation.
30      Existing work provides several foundations for this task. Static type checkers propagate declared
31   and inferred types and refine them under control-flow conditions [10, 16]. Pyinder combines au-
32   tomatic type inference, type-based calling contexts, and member-type analysis to detect Python
33   type errors [11]. Annotation inference supplies another source of type information. For example,
34   PyTIR infers repository-level annotations by resolving dependencies among program entities and
35   correcting type-checker conflicts [18]. These developments improve the information available for
36   checking Python programs and motivate examining how that information describes execution.
37      A central difficulty is that type state changes during execution. A branch can establish that an at-
38   tribute contains a string, while a subsequent helper call replaces that string with bytes. The helper’s
39   return type may remain None, and the attribute declaration may permit both types. Nevertheless, a
40   later string concatenation has become invalid. The same operation can thus be valid before the call
41   and invalid afterward. When the update also depends on a branch condition or the selected callee,
42   its effect must remain associated with that condition. Recording the possible types of parameters,
43   returns, and attributes independently does not preserve which state a particular call establishes.
44   The gap concerns how changing type states affect error judgments across procedure boundaries.
45      We study how to detect Python type errors by modeling type state and tracking its changes
46   interprocedurally. Our approach relates the state supplied to a function to the state established
47   by its execution, then uses that relation to check subsequent operations. This requires addressing
48   three challenges.
49

50      Modeling type-state changes across calls. The representation must connect the same object loca-
51   tions before and after a call, retain the conditions governing their updates, and expose the oper-
52   ation requirements encountered along the way. Normal entry–exit relations describe successful
53   effects, whereas error detection also needs the state preceding an intermediate failure. A useful
54   model must preserve both the relation between conditions and effects and the order in which
55   checks and updates occur.
56
57      Extracting relations from implicit type behavior. For a function with unknown inputs, one source
58   operation can admit several type combinations. Addition, for example, can represent integer arith-
59   metic, string concatenation, or a repository-defined operation. Each combination can establish
60   different output types and state effects. The extraction procedure must recover these alternatives
61   while reusing computations whose type behavior is independent of the unknown inputs.
62
        Detecting errors from propagated relations. At a call, the analyzer must bind formal objects to ac-
63
     tual objects, propagate applicable effects, and check operations against the state that immediately
64
     precedes them. A resulting conflict requires examining whether the inferred relation accurately
65
     captures the relevant execution. This requires connecting the conflicting operation to the condi-
66
     tions, writes, and callee behavior that produced its operands, and updating dependent judgments
67
     when that relation changes.
68
        We address these challenges with a type-state relation model and an analysis built around that
69
     model, implemented in PyTT. A function summary connects entry conditions, an ordered event
70
     graph, and projected exit states. Events retain guards, operation requirements, state updates, calls,
71
     and exception behavior. To construct summaries, the analyzer shares entry-independent facts and
72
     uses a large language model (LLM) to propose implicit type alternatives within explicit source
73
     paths. It then composes summaries at calls on a fixed call graph constructed using pyflow. Inferred
74
     relations participate in propagation immediately. When an operation or annotation check produces
75
     a conflict, the analyzer expands the necessary callee type paths, reconstructs the relevant error
76
     trace, and re-infers their behavior in context. Relation revisions invalidate dependent results and
77
     trigger reanalysis of affected callers.
78

102   2 Background and Motivating Example
103   2.1   Dynamic Typing and Mutable State in Python
104
      Python associates a type with each object, while a name can be rebound to objects of different types
105
      during execution [13, 14]. Attribute assignment similarly changes the value stored at an object
106
      location. When several references designate the same object, an update through one reference
107
      affects subsequent accesses through the others. A call can therefore change the types encountered
108
      by its caller through both its return value and updates to shared objects or global bindings.
109
         Duck typing determines whether an operation is applicable from the behavior supported by
110
      its operands [15]. The runtime objects and their classes determine method lookup and operator
111
      dispatch. Different classes can support the same operation with different result types and state
112
      effects. For example, two encoder objects can both provide an encode method while returning
113
      a string and bytes, respectively. Type annotations declare interfaces for static checking [19]; an
114
      annotation allowing both return types or field types still leaves the actual type at a particular use
115
      dependent on the preceding execution.
116
         We use type state for the type information about relevant bindings and object locations at a
117
      program point, together with the relations needed to judge an operation. These relations include
118
      branch conditions and object identity. A type-state transition describes the change caused by a
119
      statement or call. A function’s type-state relation connects its input state and execution conditions
120
      to its return value and caller-visible updates. Flow sensitivity tracks changes between program
121
      points; path sensitivity retains the association between conditions and the states they establish. If
122
      prepare(obj, binary) writes bytes when binary is true and a string otherwise, a later string
123
      operation under not binary uses the effect associated with that condition.
124
125   2.2   Hoare Triples and State Relations
126
      Hoare logic expresses a program’s behavior using assertions about its state [4, 12]. A triple
127
128
                                                          {𝑃} 𝐶 {𝑄}                                        (1)
129   contains a precondition 𝑃 , a command 𝐶 , and a postcondition 𝑄 . Under partial correctness, every
130   execution of 𝐶 that starts in a state satisfying 𝑃 and terminates normally ends in a state satisfying 𝑄 .
131   The judgment does not require termination. Assertions can describe types, values, object identities,
132   and relations between locations. For example, with 𝑜 denoting the object referenced by msg, an
133   encoding command can relate a string in Field(𝑜, body) before the call to bytes in that same location
134   afterward.
135      The composition principle connects commands through an intermediate assertion: {𝑃} 𝐶1 {𝑅}
136   and {𝑅} 𝐶2 {𝑄} support reasoning about 𝐶1 ; 𝐶2 from 𝑃 to 𝑄 . At a function call, this requires in-
137   stantiating the callee’s assertions with the caller’s arguments and object identities. The resulting
138   assertion supplies the state in which the next operation is checked.
139      Our representation uses this assertion-based view to connect function entries and exits, while
140   retaining the intervening operations as an ordered event graph. A case (𝑝, 𝑚, 𝑞) contains an entry
141   applicability assertion 𝑝 , ordered behavior 𝑚, and a projected normal-exit assertion 𝑞 . The behavior
142   records the checks and updates that establish the exit, including prefixes ending in an operation
143   failure. This makes intermediate states and their supporting operations available to the detection
144   and refinement procedures in Section 3. Entry applicability and internal operation requirements
145   serve distinct roles: the former selects a relation case, and the latter is checked against the state at
146   its execution point.

148   2.3     Type-Error Categories and Analysis Entries
149
      An operation requirement follows from the semantics of the executed operation, such as com-
150
      patible operands for addition or a callable receiver with valid argument binding. An annotation
151
      declares an interface against which inferred behavior can be checked. Runtime type errors con-
152
      cern operation failures; annotation-contract errors concern semantic incompatibility between a
153
      declaration and behavior. Each category has its own confirmation rule in Section 3.5.
154
         The analysis takes declared entries. An open function entry supplies symbolic arguments and
155
      relevant object and environment state; its input requirements are inferred from function behavior.
156
      A repository entry includes the initialization and calling sequence establishing that state. Reports
157
      identify the entry under which a conflict is checked. The targeted runtime failures involve incom-
158
      patible operands, invalid argument binding, non-callable objects, missing modeled attributes, and
159
      unsupported iteration or indexing protocols. Exception propagation is part of the judgment: a
160
      protocol failure handled within the entry is recorded as a handled failure.

      3.2         Modeling Type-State Relations
276
277      Versioned state. An analysis state is 𝐴 = (Γ, 𝐻 , 𝜙). The environment Γ maps scoped variable
278   bindings to versioned value symbols. The heap 𝐻 records the presence, value, type, and reference
279   information of object locations. The formula 𝜙 retains conditions and relations among symbols.
280   An instance attribute is identified by Field(𝑜, 𝑎), where 𝑜 is the object identity and 𝑎 the attribute
281   name. Class attributes have locations associated with their class objects, separate from instance
282   locations. Global bindings are qualified by their defining module.
283      Assignment creates a fresh value version at the updated binding or location. A fact about the
284   previous version remains a fact about that value, while subsequent reads use the new version. Ref-
285   erence information connects aliases to the same object identity. Presence distinguishes an absent
286   attribute, a present attribute whose value is None, and unknown presence. Type terms include
287   classes, subclass alternatives, container types, literal types, symbolic types, unions, and an un-
288   known type. Semantic predicates describe relationships such as operand compatibility and the
289   type of an operation’s result.
290      Alternative states retain complete relations. If an encoder choice is associated with a particular
291   field update, each alternative keeps that association. This representation directly supports the dis-
292   tinction between the illustrated call and its text-encoder alternative in Section 2.4: the same field
293   location receives different value versions under different encoder cases.
294

340   g. The depicted callee contract has an integer entry and integer return, allowing the analyzer to

      3.4   Phase II: PSTC Generation
358
359      Type Path Extraction. The analyzer explores explicit source paths in 𝐶𝐷 within the configured
360   bounds. Each template retains guards and operations in execution order, together with applica-
361   ble facts from Phase I. The Type Paths shown in Figure 2 are these templates. A source path can
362   support several implicit type behaviors: x + y, for example, can describe integer addition, string
363   concatenation, or an operation implemented by repository classes. Resolving these alternatives
364   associates each operand combination with its result and state effects.
365
         Type Constraint Resolution. The LLM receives the explicit path, relevant use-site facts, repository
366
      type information, and available callee PSTCs. It proposes implicit input/output combinations and
367
      corresponding entry and exit assertions. The analyzer assembles them with the ordered checks and
368
      effects from both 𝐶𝐼 and 𝐶𝐷 . Source paths determine the locations and ordering of the operations to
369
      which each candidate relation applies. Candidate records retain their inference context and source
370
      dependencies for subsequent inspection. The resulting cases constitute the function’s PSTC.
371
         Inferred relations participate in propagation before conflict validation. At an input state not cov-
372

694   5 Threats to Validity
695      Construct validity. Runtime type errors and annotation-contract errors measure different prop-
696   erties. An open-entry failure can describe an admissible symbolic calling state without establish-
697   ing a failure reachable from a repository entry. Likewise, an annotation conflict need not cause
698   a runtime exception in an existing call. Our category-specific metrics, declared entries, and cross-
699   category links preserve these distinctions. Manual judgments about reachability, intended inter-
700   faces, duplicate root causes, and exception handling can affect precision. The source and behavioral
701   evidence retained with each report make these judgments inspectable; the adjudication procedure
702   is specified in Section 4.1.
703
704      Internal validity. LLM-generated relations can omit legal type behaviors or introduce incorrect
705   ones. Conflict-driven expansion checks disputed relations, but unresolved source semantics and
706   incomplete context can still prevent a decision. The method does not establish soundness or com-
707   pleteness for arbitrary Python programs. The fixed pyflow call graph also bounds the callees avail-
708   able for propagation and expansion; a missing target cannot be recovered by revising a type-state
709   relation alone. Dynamic attribute behavior, reflection, native extensions, unknown dependency ef-
710   fects, and bounded loop or recursive exploration can affect coverage. These cases retain unresolved
711   or unsupported outcomes rather than being treated as confirmed absence of errors.
712      Ablation differences can arise from semantic coverage or budget consumption as well as the
713   representation being studied. Matched entries, rules, and confirmation criteria help isolate these
714   factors. We retain the causes of undecided targets and compare intermediate failures in the rela-
715   tional and direct-body alternatives. Differences between tools’ dependency models and supported
716   Python features remain relevant to the whole-tool comparisons.
717
         External validity. Public GitHub fixes emphasize errors that developers discovered and chose
718
      to repair. Repository selection, issue wording, dependency availability, and the required bug-fix
719
      pairing can therefore affect the sampled error distribution. The recent collection interval reduces
720
      exposure to older public examples but does not establish that the benchmark is absent from model
721
      training data. Model training cutoffs and corpus membership may be unknown. Independent dis-
722
      covery repositories test another setting, although their domains and selected entries still bound
723
      generalization.
724
725      Conclusion validity. The best-of-three protocol reports selected effectiveness rather than ex-
726   pected performance from a single run. It can favor methods with greater run-to-run variability
727   and depends on the selection metric and aggregation unit. Consequently, the reported effective-
728   ness cannot be interpreted as mean reliability. Retaining all run records and accounting for all three
729   runs’ cost exposes the associated variability and resource expenditure. Model revisions, decoding
730   settings, and external service latency can also change outcomes and cost.

732   6 Related Work
733     Python type checking and type-error detection. Python’s annotation system supplies optional
734   type declarations, and structural protocols describe behavior shared by different classes [5, 19].
735
      16                                                                                                           Anon.


736   Checkers combine this interface information with inference and local narrowing [10, 16]. Empir-
737   ical studies examine how gradual typing affects checker behavior and which types are needed to
738   describe dynamic objects [17, 20]. Our analysis focuses on the state at an operation after preced-
739   ing calls have changed shared locations. The relevant relation connects a calling condition to the
740   particular update that reaches that operation.
741      Pyinder is a close task-level comparison. It infers types, analyzes functions under parameter-
742   type contexts, and aggregates and filters member types to identify Python type errors [11]. We
743   study a representation that keeps entry state, execution conditions, ordered requirements, and
744   caller-visible updates together. Actual object bindings instantiate this representation at calls, while
745   conflict dependencies identify the callee type paths used for re-inference. The whole-tool compar-
746   ison measures detection outcomes; the controlled variants examine the roles of relation preserva-
747   tion and feedback.
748
749      Type inference and generated annotations. Annotation inference reconstructs interface types
750   from code and repository context. PyTIR models entity dependencies and iteratively updates types
751   and dependencies with checker feedback [18]. Its evaluation includes annotation accuracy and
752   diagnostics introduced by generated annotations. Our target is the original program’s operation
753   behavior and existing annotation contracts. The state analysis uses a fixed pyflow call graph [3]; re-
754   finement changes type-state relations and their dependent judgments. The inference-plus-checker
755   baseline evaluates how annotation generation serves this detection task, separating original errors
756   from generated-interface inconsistencies.
757
758
         Relational and compositional program analysis. Hoare logic connects assertions at program en-
759
      try and exit [4]. Compositional symbolic execution reuses procedure behavior at calls [2], while
760
      abstract interpretation provides a foundation for reasoning about program states and their rela-
761
      tions [1]. MOPSA applies abstract interpretation to Python type analysis, including state relations
762
      and control and exception behavior [8].
763
         Our model uses these relational and compositional principles for Python type-error detection.
764
      Its cases preserve ordered checks and writes along with entry and exit assertions, so intermedi-
765
      ate failure dependencies remain available during composition and refinement. The accompanying
766
      construction procedure shares entry-independent facts and proposes implicit type alternatives;
767
      detection revisits disputed alternatives through selectively expanded type paths. The comparison
768
      with failure-preserving relational summaries and direct body analysis evaluates these representa-
769
      tion and construction choices under matched rules.

      7 Conclusion
772   We present an interprocedural type-state analysis for detecting Python type errors. The model con-
773   nects function inputs and execution conditions to ordered operation requirements, shared-state
774   updates, and exits. The analysis constructs and composes these relations, then uses conflicts to
775   select callee type paths for expansion and contextual re-inference. Dependency-driven revisions
776   update affected caller judgments. Runtime type errors and annotation-contract errors retain dis-
777   tinct confirmation criteria and results. The evaluation measures paired detection, diagnostic pre-
778   cision, unresolved outcomes, and complete analysis cost. The central design connects each error
779   judgment to the state established by the calls and updates preceding the operation.
